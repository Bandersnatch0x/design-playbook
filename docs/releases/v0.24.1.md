# v0.24.1

Patch release prepared 2026-09-19. It adds Zed as a tier-2 adapter target
and widens the release pipeline's npm registry verification window that
produced two false-negative verify failures on v0.23.0 and v0.24.0.

## Zed adapter (30 agents)

`npx design-playbook init zed` now renders a tier-2 surface:

- **`.rules`** carries the shared digest block (orchestrator contract +
  sub-skill index) as a marker block, so re-running init refreshes it in
  place. Zed reads project rules through a first-match priority list with
  `.rules` on top, so the renderer **avoids creating a new `.rules` while a
  documented lower-priority competitor rules file exists** (`.cursorrules`,
  `.windsurfrules`, `.clinerules`, `CLAUDE.md`, Copilot instructions) —
  creating one would silently shadow the user's own rules. An existing
  `.rules` always refreshes normally, because that is the file Zed already
  reads.
- **`.zed/settings.json`** gains `context_servers` entries for both bundled
  MCP servers through the merge-safe JSON path (user-managed keys are
  preserved verbatim). The stdio entry shape follows the official settings
  documentation (string command form); the community-visible object form
  stays untouched when a user already manages entries that way.

The packaged doctor's adapter lifecycle check covers the new artifacts
automatically; the fresh-init zero-false-positive matrix extends to 29
non-native agents.

## Release pipeline hardening

Both release workflows' "Verify npm registry" step polled with an effective
90-second window (18 × 5s) while provenance verification already allows
600 seconds (20 × 30s); CDN replication lag beyond 90 seconds failed the
step on v0.23.0 and v0.24.0 even though both publishes had succeeded. The
registry poll is aligned with the provenance-scale window.

## Verification

Zed renderer tests cover fresh-init shape, the avoidance tri-state,
competitor-present refresh, user-content append, merge-safe user keys, and
idempotent re-init; a clean-directory dogfood loop (init → doctor →
re-init → re-check) is recorded with zero false positives. Existing
adapter behavior is regression-pinned (frontmatter placement and CLI/dry-run
byte-compatibility unchanged). Release gates (validate, seam, adapter
floor) green.
