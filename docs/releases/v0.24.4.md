# v0.24.4

Patch release prepared 2026-09-21. It repairs the DSH listing contract —
no runtime code changes. Two defects shipped together: the npm tarball never
contained the `cordis.patch.yml` its manifest declares as `dsh.bundle.patch`,
and the manifest carried no per-release DSH compatibility declaration.

## npm tarball missing the declared bundle patch

`packages/design-playbook/package.json` declared
`dsh.bundle.patch: "./cordis.patch.yml"` but did not list that file in
`files[]`, so every published tarball since v0.14.0 omitted it. DSH reads the
overlay by path inside the installed package, so a profile that listed
`design-playbook` as a bundle failed to compose at all:

```
dsh: failed to read overlay <profile>/node_modules/design-playbook/cordis.patch.yml:
     ENOENT: no such file or directory
```

`cordis.patch.yml` is now an explicit `files[]` entry. This is a packaging
fix only; the patch content is unchanged.

Three regression guards were added so neither defect can return silently,
since both are manifest-only contracts with no local symptom:

- `scripts/validate.py` checks that `files[]` ships the declared
  `dsh.bundle.patch` — for both DSH-installable packages.
- `scripts/validate.py` checks that `dsh.compatibility.dshReleases` is
  present and well formed: exact DSH versions as keys (a range is not
  installable evidence), verdicts drawn from
  `compatible` / `incompatible` / `unknown`.
- `tests/test_release.py` unit-tests the compatibility block parser.

## Explicit DSH compatibility declaration

Both DSH-installable package manifests now carry
`dsh.compatibility.dshReleases`, which DSH STORE requires per exact release
(a range alone is not installable evidence):

| DSH release | `design-playbook` | `dsh-design-playbook` |
| --- | --- | --- |
| `0.1.5-rc.2` | `compatible` | `compatible` |
| `0.1.6-alpha.1` | `unknown` | `unknown` |
| `0.1.6-alpha.2` | `compatible` | `compatible` |

## Verification

Each declaration was checked by composing a disposable DSH profile at that
exact CLI release and reading the composed tree back.

**`design-playbook`** (`@deepseek-ai/dsh-base` + `design-playbook`, both in
`dsh.profile.bundles`; `dsh --profile probe --dump-config`): `0.1.5-rc.2` and
`0.1.6-alpha.2` compose with the `design-playbook` layer present.
`0.1.6-alpha.1` is declared `unknown` rather than `incompatible` because that
DSH release cannot start at all, for any plugin: its `lib/profile-boot-*.js`
imports `watchUserPatches` from `@deepseek-ai/dsh-app-boot`, while its own
dependency range (`^0.1.6-alpha.1`) resolves that package to `0.1.6-alpha.2`,
which no longer exports it — the CLI dies on module instantiation before any
plugin layer is read. That is an upstream packaging defect, not a
design-playbook verdict.

**`dsh-design-playbook`** (`@deepseek-ai/dsh-base` + the bridge bundle;
`dump-config` yields rows `design-playbook-preview-mcp` and
`design-playbook-evidence-mcp`): composed on `0.1.5-rc.2` and `0.1.6-alpha.2`.
`dump-config` echoes the patch's `!!js` expressions unevaluated, so the
resolution contract was asserted separately by evaluating the same expression
(`createRequire(<profileDir>).resolve(...)`) against each composed profile:
both `design-playbook/mcp/{preview,evidence}/server.py` specifiers resolve
inside the profile's `node_modules`. `@deepseek-ai/dsh-mcp-client` is not a
profile dependency — DSH ships it as a dependency of the CLI itself (resolved
`0.1.5-rc.2` / `0.1.6-alpha.2` in the two CLI trees, satisfying the declared
`>=0.1.0-rc.6` peer range). `0.1.6-alpha.1` inherits the `unknown` above.

Profile composition and patch-path resolution are the evidence level here.
Starting the MCP servers and loading the plugin's skills and commands into a
live DSH session were not exercised.
