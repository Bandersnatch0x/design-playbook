## 0. 全局原则（矩阵的宪法，所有能力域共用）

原则 1、4 来自 CONTEXT.md 已决边界与研究工单结论；原则 2、3、5 经决议 Q7/Q8 确认为矩阵全局约束：

1. **所有权边界**（CONTEXT.md「First-party UI/UX ownership boundary」已决）：design-playbook 拥有能力矩阵、工件契约、门禁、证据语义与回流。外部参考样本 A-D 与本地学习资料只是基准输入：可以暴露缺口与冲突，但既不是产品依赖，也不是规则权威。核心模型平台中立，Web 是首个自动验证面。
2. **证据两分**（HCI 研究的核心约束，#27）：每个能力域的证据义务必须区分两级——
   - **可自动验证的复现事实**：工件结构完整性、声明↔事实一致性、确定性运行事实（动作存在/状态出现/返回保持/错误出口可执行）、术语与命名的机械一致性、证据 provenance 齐全性。
   - **需人工证据的主观结论**：主路径是否真是目标用户最重要的路径、信息层级与术语是否符合心智模型、反馈是否可理解、认知负担、满意度、审美质量、严重度与修复优先级。系统可以组织证据、指出冲突、提出待验证问题，但 verdict 需要有权的人或相应用户研究。
3. **自动化默认立场**（决议 Q8 确认）：语义判断默认 advisory；主观维度只能产生 advisory finding，不进 blocking；要成为阻断必须先经规则治理晋升（用户裁决）或项目显式声明。晋升为 machine-enforced gate 需同时满足六条——权威来源、对应用户可见风险或产品不变量、输入与通过条件确定可复现、误报/漏报成本已评估、存在修复路径与例外机制、已通过内部样本与反例验证。
4. **Provider 边界**（CONTEXT.md 术语表已决）：provider 产出 artifacts，不产出 evidence；artifact 只有被 manifest 绑定到 criterion 才成为证据；provider 不定义成功判据、不发出 verdict。设计与采集系统永远是可替换的执行面。
5. **决策权按后果分级，不按来源工作流分级**（决议 Q7 确认采纳的默认表）：

| 决定 | 默认决策权 | 门禁理由 |
| --- | --- | --- |
| 产品目标、目标用户、成功判据、非目标 | 用户确认 | 改变产品必须达成什么 |
| 实质不同的 IA 或主路径替代方案 | 用户确认 | 改变用户行为与验收范围 |
| 改变识别度/构成的视觉方向 | 用户确认 | 防止静默品牌漂移 |
| 已确认声明内的局部实现选择 | 代理自主 | 加审批是低价值摩擦 |
| blocking 处置 | 仅当改变声明或接受风险时用户介入 | evaluator 不能豁免自己的失败 |
| 规则晋升为 machine-enforced gate | 用户裁决 | 防止单一样本或单次 run 成为规则权威 |

### D1 需求成形 RS — Interactive requirement shaping

- **职责**：把模糊 UI 请求成形为确认的产品意图：目标用户/角色、代表性任务、使用情境、现有行为证据、产品约束、可用性目标、成功判据、非目标、风险、假设状态（observed/reported/assumed/open）、待研究问题；维护 `decided|assumed|open` 字段权威。
- **输入**：模糊请求；持久契约（contract.json + decisions.jsonl）；项目设计基线（DESIGN.md / design-baseline state）；既有 spec；HCI 提问原则（绑定用户/任务/环境的判据、主路径优先、用户差异是设计输入）。
- **输出**：确认的需求增量（契约字段 + 决定日志条目）；开放问题队列；run 范围 UX spec（L1-L6）。叙述性场景保存上下文，结构化 criterion 负责验证，两者互引不可互替。
- **决策权**：产品目标/用户/成功判据/非目标等 consequential 字段——**仅用户显式确认产生 `decided`**；代理只能提问、记录保守假设（`assumed`）与开放项（`open`）；`assumed` 每 run 须再确认，`open` 阻塞下游。
- **证据义务**：自动级——字段状态完整性、bind-first 阻塞、决定日志 append-only、来源漂移检测（contract_v1 + G7 已交付）。人工级——关键用户假设是否为真需要用户证据或研究证据（来源状态机器可查，真伪人工判）；不得自动生成通用可用性阈值（响应时长、步骤数、选项数只有在绑定具体用户/任务/环境后才有意义）。
- **宿主边界**：访谈对话由宿主代理执行（可替换）；持久契约、决定日志、字段状态语义、问题队列工件为第一方。
- **定稿依据**：#26 判「部分」——契约机械层完整，但无有状态访谈、问题队列、确认批次、对话→契约的受控投影。**决议 Q3**：会话工件（待答问题队列、假设批次、确认批次）为第一方持久工件，确认后投影到契约与 spec——持久权威仍是契约。决策模型与会话工件生命周期细节留给 #28。

### D2 交互建模 IM — UX interaction specification

- **职责**：以「用户目标 → 意图/选择 → 可发现动作 → 系统状态变化 → 可感知反馈 → 完成或恢复」为最小单元建模；表达主路径/必需低频路径/边缘情形、逐页职责与进入预期/成功判据、决策点、跨页返回状态保持、逐页五态（初始/加载/成功/失败/空，含权限/超时变体）。
- **输入**：确认的需求增量（D1 输出）；用户任务分解；平台约束声明。
- **输出**：交互模型（页面/视图职责表、路径表、状态矩阵），与 L6 AC 一一对应可追溯。
- **决策权**：结构性 IA 或主路径替代方案实质不同时——用户确认；页面职责、路径、五态枚举完整性——规则/门禁；模型内部细节——代理。
- **证据义务**：自动级——每条 L6 有可达路径、每页必需状态齐全、术语与契约一致（存在性与完整性可门禁）。人工级——「哪条路径最重要」「反馈是否足够显著」「跨视图记忆负担」只能作为风险提示或待验证问题（元素计数不能证明认知负担）。
- **宿主边界**：纯声明工件，无执行面；任何流程图/原型工具只是可选投影。
- **定稿依据**：#26 判「部分」——L2-L5 层次存在但缺逐页职责、进入预期、决策点预算、返回保持、显式五态，且 G1 不读这些语义。**决议 Q2**：以深化现有 `spec.md` L2-L5 的形式落地（逐页职责、五态、路径为结构化字段），配套最小门禁（存在性 + 每页五态完整性 + 每 AC 有可达路径），不新增第三 SSOT；若 #28/#32 原型中发现 spec 过载再评估拆独立工件。schema 细节与门禁字段清单留给 #32。

### D3 设计决策 DD — Tool-neutral design decisions

- **职责**：编码前比较设计方向：待决问题、候选方案、比较轴、取舍、保真度与遗漏、预期影响、证据计划、选择/拒绝理由、确认人、残余风险、provenance。
- **输入**：UX spec（D2）；项目设计基线（design-baseline 已确认的 DESIGN.md）；约束。
- **输出**：版本化 decision report（schemaVersion、稳定决策 ID、候选、确认状态）；既有产品基线的发现/确认/重验记录。
- **决策权**：实质改变结构或识别度的方向——用户选择；已确认基线内的视觉方向——用户仅在识别度/构成改变时确认（防静默品牌漂移）；确认声明内的局部实现选择——代理自主（低价值摩擦不加门）。
- **证据义务**：自动级——决策元数据完整性、确认记录完整性（G5 校验确认工件完整性，已交付）。人工级——方案哪个更适合任务需要原型比较或用户证据（R-08）；预览偏好不能自动提升为最终验收。
- **宿主边界**：设计生成器/预览运行时是可替换 provider；决策事务（transaction）拥有决定权与持久化，完整性规则属 bundled runtime；报告 schema 第一方。
- **定稿依据**：design-baseline 子能力判完整（保留）；ui-picker + decision-report 判「部分」——无版本化 schema、无候选/取舍/拒绝理由/决策 ID。协议细节留给 #31。

### D4 实现评审 IR — Dual-track implementation review

- **职责**：双轨审查已实现界面——**产品轨**（实现是否支持已确认的用户目标、主路径、验收判据）与**交互轨**（动作是否可发现、状态是否可解释、错误是否可恢复、信息是否按任务组织、跨视图状态是否闭环）；外加**横切适用性矩阵**——**决议 Q5**：首版横切 = 无障碍 + 响应式；国际化、性能感知、安全体验作为注册表中的 advisory 占位规则（显式适用谓词，不静默跳过；运行时证据不可得记 Blocked 而非静默跳过）。没有对应契约的发现回流 D1，不在评审中现场发明产品要求。
- **输入**：源码、渲染 UI、运行时 artifact、交互模型（D2）、AC 清单、规则注册表（D7）、组件/模板/工艺声明。
- **输出**：结构化 findings（issue/source/fix/severity + owning declaration + 证据 provenance 分类）；point-back.md；verdict 仅 Pass 或 Recirculate（分数与清单是诊断，不是验收）。
- **决策权**：结构门禁（每条 AC 恰一条证据行、Pass 全 pass、blocking 有精确 closure）——机器（G2-G4 已交付）；blocking 处置——仅当改变声明或接受风险时需用户（evaluator 不能豁免自己的失败）；局部实现修复——代理。
- **证据义务**：自动级——源码/运行事实取证（截图、无障碍树、交互轨迹的绑定完整性，G6 已交付）、确定性检测器命中、结构完整性。人工级——观察是否真实覆盖主路径、建议是否正确、严重度、认知负担、满意度（启发式命中不得直接判阻断缺陷；未命中不得判体验通过）；**决议 Q8**：主观维度默认 advisory，不进 blocking，须先经规则治理晋升或项目声明方可阻断。
- **宿主边界**：检测器、浏览器检查、无障碍扫描器是可替换工具；finding schema、证据类型分级、verdict 语义第一方。
- **定稿依据**：#26 判「部分」——验收闭包已成形，但广度未覆盖完整主路径与横切矩阵，且大部分判断是代理协议。双轨与证据模型细节留给 #29。

### D5 证据 EV — Evidence binding & semantics

- **职责**：把 provider artifact 绑定到 criterion，成为唯一合法证据；为证据增加方法语义：`method`（static inspection / runtime observation / expert review / user test / interview / survey / field observation / telemetry / controlled comparison）、`population/context`、`observation`（事实）与 `interpretation`（解释，分离）、`scope/limitations`、`ethics`（同意/匿名化/保留期限，涉人研究时必需）。
- **输入**：声明的 criterion（L6）；provider 产出的 artifacts（截图、轨迹、测量、研究记录）。
- **输出**：manifest 条目（append-only，Contract 与 Runtime 唯一接缝）；evidence ledger 行（required proof / observed proof / pass|fail|blocked|N/A）。
- **决策权**：绑定与快照完整性——机器（G6 已交付）；pass/fail 判断——evaluator（不是 provider，也不是 manifest）；N/A——须附理由。
- **证据义务**：自动级——criterion↔artifact 绑定、capture contract（viewport/freeze/schemaVersion）完整性、provenance 齐全性。人工级——observation 的解释与可推广范围（小样本不能自动普遍化；多种弱证据相加不等于强结论）；代理不得以自身评分宣称真实用户满意/信任/认知负担低。
- **宿主边界**：capture provider 完全可替换（Playwright MCP / 手动 / 未来适配器）；manifest 与证据语义第一方。
- **定稿依据**：#26 判 capture/binding 机械层完整但「有截图≠实现通过」——方法语义缺失。**决议 Q1**：证据确认为独立一等能力域。证据模型细节留给 #29。

### D6 回流 RC — Point-back repair & re-validation

- **职责**：失败不一律指向实现层。回流目标分五类：requirement（用户/任务/情境/成功标准不完整）、interaction model（状态/路径/异常/恢复遗漏）、design decision（方案假设失败或取舍未记录）、implementation（实现偏离已确认模型）、evidence plan（方法不能回答问题/样本不匹配/证据不足）。修复取最小集：失效受影响证据、给出恢复点、只重跑受影响 criterion 与相邻主路径，保留原失败证据与修订原因。
- **输入**：finding（含 observable → owning declaration 映射）；声明层次。
- **输出**：最小修复指令；失效证据集；恢复点；下一恢复动作。
- **决策权**：路由与失效范围——规则（observable→owning layer 映射已交付）；轮次预算（两轮停止）——规则（需机器计数化，现为代理执行）；改变声明类回流——用户确认修订。
- **证据义务**：自动级——closure 精确性（G4 已交付：blocking 不得被删除通过）、失效范围可计算。人工级——修订后的声明是否真的解决了根因。
- **宿主边界**：实际修复与重评执行是宿主代理；回流协议、失效语义、恢复点状态第一方。
- **定稿依据**：#26 判「协议较强、执行靠代理」——无循环计数、无持久循环状态机。状态机细节留给 #32。

### D7 规则治理 RG — First-party rule registry & governance

- **职责**：统一所有评审规则的注册表：稳定规则 ID 与版本、能力域、**权威级别**（硬约束 / 项目声明 / 平台惯例 / 实测阈值 / 建议美学）、适用谓词（防止某平台建议变成普适规则）、可观测量与用户影响、检查方法（static/runtime/interaction/measurement/human-review）、所需证据类型、严重度规则（基于任务/用户影响而非措辞强度）、误报与例外条件、point-back owner、再验证指令、provenance（独立撰写与验证记录，不把外部样本当权威）。
- **输入**：候选规则（来自 D8 信号、平台硬约束、项目声明、内部撰写）；运行历史。
- **输出**：版本化注册表记录；豁免记录（带理由）。
- **决策权**：晋升为 machine-enforced gate——**仅用户裁决**（六条晋升标准，见原则 3）；项目声明可覆盖建议美学，但不得覆盖硬约束（无障碍/安全需要独立权威级别，而非更强的措辞）；无上下文数字门禁与「专家判断冒充用户证据」显式禁止。
- **证据义务**：自动级——规则治理元数据完整性、冲突解析确定性（项目覆盖与硬约束须可机械判定）。人工级——规则是否值得晋升、误报成本评估。
- **宿主边界**：规则目录与治理语义第一方；规则执行器（检测器/扫描器）可替换。
- **定稿依据**：#26 发现已发货矛盾——craft-guard 技能允许 N/A，检测器协议只允许 `clear|hit|blocked`，校验脚本只收后三者：规则分散在技能/参考文档/校验脚本中，无单一注册表。**决议 Q1**：规则治理确认为独立一等能力域；**决议 Q4**：craft-guard 八检测器并入统一注册表作为 advisory detector（带权威级别、适用条件、误报条件、point-back owner），craft-guard 技能保留为注册表的引用/执行说明层，迁移时一并修复状态枚举矛盾（ID、豁免、fixture 迁移细节留给 #30）。

### D8 跨运行学习 LR — Cross-run learning

- **职责**：聚合的是「在何种用户、任务、环境和证据方法下重复出现的问题」，不是无上下文计数；为满足条件的稳定复现生成规则候选（进入 D7 队列），保留适用条件、误报记录与来源。
- **输入**：归一化 findings 与 run outcomes（跨 run 严格文本归一化计数已交付）。
- **输出**：repeat pattern 计数（JSON 契约面）；规则候选队列。
- **决策权**：计数——机器；**计数永不自动晋升规则、永不自动改严重度**（v0.9 语义保留）。
- **证据义务**：自动级——归一化计数、门禁投影。人工级——复现是否构成规则（进 D7 人工裁决）；叙事学习与自动写回基线维持禁止。
- **宿主边界**：无执行面；读模型第一方。
- **定稿依据**：#26 判「信号发现完整、晋升闭环缺失」。**决议 Q6**：首版仅做注册表 schema + 候选队列 + 晋升标准定义，晋升闭环（候选 → 人工裁决 → 版本化晋升/驳回 → 受影响规则与 run 回归验证）的执行延后。治理细节留给 #30。

## 5. 已确认决议（2026-08-14，用户裁决：全部按建议采纳）

| 题 | 问题 | 决议 |
| --- | --- | --- |
| Q1 | 能力域划分粒度：证据与规则治理是否独立成域？ | **A：8 域**——证据（EV）与规则治理（RG）独立成域：证据语义与规则治理都是横切关切，与 #29/#30 等后续工单一一对应 |
| Q2 | 交互建模的工件形态：深化 spec 还是新增工件？ | **A：深化现有 spec.md L2-L5**——逐页职责、路径、决策点、逐页五态作为 L2-L5 结构化字段 + 最小门禁（存在性、每页五态完整性、每 AC 有可达路径）；不新增第三 SSOT；schema 细节留 #32 |
| Q3 | 交互式需求成形的会话权威：会话状态是否为第一方持久工件？ | **A：是**——待答问题队列、假设批次、确认批次为第一方持久工件，确认后投影到 contract.json/decisions.jsonl 与 spec；持久权威仍是契约；会话工件生命周期留 #28 |
| Q4 | craft-guard 八检测器的归宿？ | **A：合并入统一规则注册表**——作为 advisory detector 记录迁入 D7（带权威级别、适用条件、误报条件、point-back owner），craft-guard 技能保留为注册表引用/执行说明层，一并修复状态枚举矛盾；迁移细节留 #30 |
| Q5 | 首版横切评审矩阵的范围？ | **A：首版 = 无障碍 + 响应式**——国际化、性能感知、安全体验作为注册表中的 advisory 占位规则（显式适用谓词，不静默跳过） |
| Q6 | 学习域首版边界：是否包含规则晋升闭环？ | **B：首版仅注册表 schema + 候选队列 + 晋升标准定义**——晋升闭环（候选 → 人工裁决 → 版本化晋升/驳回 → 回归验证）执行延后 |
| Q7 | 决策权默认表：是否采纳「按后果分级」的门禁表？ | **A：采纳**——按后果分级的默认表（见原则 5 的表）：产品目标/用户/成功判据/非目标、实质不同的 IA/主路径替代、改变识别度的视觉方向→用户确认；确认声明内的局部实现→代理自主；blocking 处置仅当改声明或接受风险时用户介入；规则晋升→用户裁决 |
| Q8 | 需人工证据的主观结论在 verdict 中的地位？ | **A：默认 advisory**——主观维度（认知负担/满意度/审美/术语适配/心智模型）只能产生 advisory finding，不进 blocking；要成为阻断必须先经规则治理晋升（用户裁决）或项目显式声明；可复现事实维持现有机器门禁 |
